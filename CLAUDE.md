# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

An osu! tournament site: a Rust (axum + sqlx/Postgres) backend and a React + TypeScript (Vite) frontend. Users log in with osu! OAuth, can optionally link Discord, and map poolers build per-stage map pools that are published to a public page.

## Commands

A single `.env` at the repo root (copy from `.env.example`) feeds the backend (dotenvy searches parent dirs), the frontend (`envDir: ".."` in `frontend/vite.config.ts`, so only `VITE_*` vars reach it) and docker-compose.

```bash
# Backend (from backend/) — needs a reachable Postgres at DATABASE_URL
cargo run                 # serves on 127.0.0.1:8080, runs migrations on startup
cargo check / cargo clippy / cargo fmt

# Frontend (from frontend/)
npm install
npm run dev               # http://localhost:5173, calls the API at http://localhost:8080
npm run typecheck         # tsc only
npm run build             # tsc && vite build

# Everything in one container + Postgres
docker compose up --build # http://localhost:8080
```

There are no automated tests and no linter config for the frontend. `tsc` runs in strict mode with `noUnusedLocals`/`noUnusedParameters`, so unused code fails the typecheck.

For testing, set `DEV_LOGIN=true` in `.env`: the backend then mounts `/api/dev/*` (`handlers/dev.rs`) and the frontend bundles a floating account switcher (`components/DevSwitcher.tsx`, behind the build-time `__DEV_LOGIN__` constant from `vite.config.ts`) with buttons to reseed or clear dummy data. Dummy accounts have negative `osu_id`s (stages can't be marked that way, so the seed reuses stages by name and `clear.sql` only deletes seeded ones that have no categories); the seed lives in `backend/seed/` (it also gives the concluded qualifier lobby seven teams and a chat that plays the whole qualifier pool (the first map twice), W1 two rooms with saved chat, the first live winners match a chat stopped mid-way through its freemod map, every concluded match saved map results with player scores and mods (a 5-4 one ends on TB), the first two upcoming matches some proposed times with the players' notices, Rank Uçtu a rank-limit notice, and every seeded stage the pool categories it's missing (by name), filled with real ranked maps added by DevPooler; `clear.sql` deletes the chat of the matches it removes and the categories holding only dummy-added maps) (also runnable with `psql "$DATABASE_URL" -f backend/seed/clear.sql -f backend/seed/seed.sql`, minus the team banners in `seed/banners/`, which `db/dev.rs` adds) and must be kept in step with schema changes. "Reseed + live match" (`POST /api/dev/seed/live`, shown to a real account) reseeds and then runs `seed/live.sql`, which teams the signed-in account with a dummy against a dummy team in a bracket match starting now with no room, refereed by DevReferee, so a real osu! room can be run with the real player in it. It defaults to off. It works over https too, so testers can use it on the live server while the site isn't public, but anyone who can reach the site can then sign in as any account (hosts included), so it must be turned off before launch.

The first host has to be set by hand in SQL: `UPDATE osu_users SET roles = '{host}' WHERE osu_id = <id>;`

## Architecture

### Backend (`backend/src`)

- `main.rs` builds `AppState` (oauth clients, `PgPool`, reqwest client, `Arc<Config>`, cached osu! app token) and mounts `/auth/*` (OAuth flows) and `/api/*` (JSON). If `STATIC_DIR/index.html` exists, it also serves the built frontend as a SPA fallback. This is how the Docker image serves both from one origin, with `VITE_API_URL` built empty.
- `config.rs`: clap `Config` from env vars, each also settable as a CLI flag. Whether cookies are `Secure` comes from the scheme of `FRONTEND_URL`.
- `handlers/<area>.rs` each expose `routes()`; `db/<area>.rs` hold the queries. Queries use runtime `sqlx::query_as::<_, T>(...)`, not the compile-time `query!` macros, so building needs no database.
- `error.rs`: handlers return `Result<_, AppError>`. Clients only get a generic message; 5xx causes go to the log. Add a new variant there instead of returning raw status codes.
- Migrations in `backend/migrations` are embedded with `sqlx::migrate!` and run on startup. Add a new numbered file and never edit an applied one.

### Auth and roles

- Server-side sessions (`auth.rs`, `db/session.rs`). The httpOnly `session` cookie holds a random 32-byte hex token, and the `sessions` table stores only its SHA-256, with a fixed 7-day expiry and no sliding renewal. The `AuthUser` extractor does one query per request that joins the session, `osu_users.role` and whether a Discord account is linked. Use `Option<AuthUser>` for routes that also work signed out.
- Create and end sessions only through `auth::start_session` / `auth::end_session`; they keep the cookie attributes and the stored hash consistent.
- `auth::spawn_session_cleanup` (started in `main.rs`) is a background tokio task that deletes expired sessions once at startup and then hourly.
- Roles are a set, not a ladder: a user holds any of `host`, `map_pooler`, `referee`, `streamer`, `graphics_designer`, `pool_tester`, `custom_mapper` and `commentator` (`osu_users.roles`, a `staff_role[]`; none means a regular player), ticked per user on `/admin/users` (`PUT /api/users/:id/roles`; a host can't drop their own Host). `role.rs` (`Roles`, a bitset on `AuthUser`) is mirrored in `frontend/src/auth/roles.ts`. Roles don't imply each other except that Host is allowed everything: `Roles::allows` (`hasRole`) is holding the role or being a host, and gates pages and actions (`user.require_role(Role::X)?`). Acting in a role needs the role itself, `Roles::has` (`holdsRole`): only holders of Referee/Streamer are offered for, can take and are pinged about those slots (`list_referees`/`list_streamers`, `staff_declined`), so a host who referees ticks Referee too. `Roles::can_play` (`canPlay`) lets users with no role or only Streamer, Graphics Designer and/or Commentator be in teams; the rest of the staff can't. Graphics Designer and Commentator carry no authority at all: they only list the user on `/staff`, and `isStaff` (which opens `/admin`) ignores them. All `/api/stages|categories|slots|pool|maps` routes go through `guard()` in `handlers/mappool.rs` (MapPooler or host), except that creating, renaming, reordering and deleting stages is Host-only (map poolers still publish stages and fill them), and that listing and reading stages (`GET /api/stages`, `/api/stages/:id`) go through `view_guard()`, `Roles::can_view_pool` (`canViewPool`), which also lets in Pool Tester and Custom Mapper. Those two only get the Mappool tab (access `"pool"`), which the editor shows read-only to anyone not allowed MapPooler (no adding, moving, dropping, settings; notes shown but not editable, `readOnly` on `EditableNote`, `viewOnly` on `MapCard`); the Maçlar tab is access `"matches"` (holders of Host, MapPooler, Referee or Streamer). User admin is Host-only.
- Rules (`handlers/rules.rs`, `db/rules.rs`): the single-row `rules` table holds osu! BBCode (seeded by migration 0035 from the previous tournament's forum post). `GET /api/public/rules` serves it to `/rules` (`pages/RulesPage.tsx`, with a contents list built from its `[heading]`s); hosts edit it on `/admin/rules` (`pages/admin/RulesAdminPage.tsx`: source, toolbar and live preview) through `PUT /api/rules`, which sends the `updated_at` it loaded and gets a 409 if another host saved since. `lib/bbcode.ts` parses the forum's tags into a tree and `components/BBCode.tsx` renders it as React elements (never as HTML), letting links through only for http(s)/mailto and images only for http(s).
- The public `/staff` page (`pages/StaffPage.tsx`, "Ekip" in the nav) lists everyone holding a role, grouped by role (someone with two roles shows in both), from `GET /api/public/staff` (`db::user::list_staff`), which carries each one's linked Discord: staff Discord accounts are public on purpose.
- Because the roles are read on every request, role changes and logouts take effect immediately. No cookie needs re-issuing.

### Map pool domain (the core of the app)

The schema has changed a lot across migrations; the current model is:

- `stages` (ordered by `position`, with a `published` flag) → `stage_categories` (ordered, with a `color` `#rrggbb`) → `category_slots` (ordered, with `editor_notes`).
- At most one stage has `is_qualifier` (partial unique index `stages_qualifier_key`): the map pool the qualifier lobbies play. Hosts pick it on `/admin/stages` (`PUT /api/stages/qualifier`); bracket matches point at their stage with `bracket_matches.stage_id` instead.
- `pool_maps` holds each map **self-contained**: the beatmap metadata plus the mod-adjusted stats are copied in when the map is added, and there is no beatmap cache table. `slot_id IS NULL` means the map is in the global **generic pool** shared by all stages. Otherwise it fills exactly one slot (`UNIQUE(slot_id)`). Deleting a slot sends its map back to the generic pool. The same beatmap under different mods is a separate row.
- Mods are a concatenated 2-letter acronym string (`"HDDT"`) stored on the map. Stats are fixed when the map is added (`resolve_stats` in `handlers/mappool.rs`): SR/AR/OD come from the osu! difficulty-attributes API (skipped for nomod), and CS/BPM/length are computed in `mods.rs`. They are never recomputed later. HP is not stored.
- Public vs editor views: `editor_notes` (on slots and maps) must never reach the `/api/public/*` routes. These routes use separate `Public*` row structs and only return published stages. Keep that split when adding fields.
- osu! API calls (`osu_api/`) use an app token from the client-credentials flow, cached in memory in `AppState.osu_app_token`.

### Teams (2v2)

- `teams` / `team_members` (a player's `user_id` is the primary key, so one team per player) / `team_invites`. A team is created with both players when an invite is accepted, and doing so drops every other invite involving either of them.
- Eligibility is `team_rank.rs`: each rank maps to a value and the pair's sum must stay at or below `LIMIT`. It's checked when inviting and again when accepting (`handlers/team.rs`).
- The inviter names the team on the invite; the name moves to `teams.name` on accept and is unique case-insensitively (`teams_name_key`). Either player can rename or disband their team, and hosts can rename or disband any team.
- Banners live in `team_banners` as bytes (small app, no object storage). The type comes from the file's magic bytes, uploads are capped at 2 MB, and `Team.banner_url` carries the upload time as a version so the image can be cached forever.
- Ranks come from osu! through `rank_refresh.rs`, using the bulk `GET /users` endpoint (50 ids per call, osu!standard stats, no country rank). The player search, the team page, inviting and accepting refresh the users involved when their rank is over 10 minutes old (`osu_users.rank_updated_at`); failures fall back to the stored ranks. Every team member is refreshed daily (a background task checks hourly against `app_settings.ranks_updated_at`, so restarts don't skip or repeat it) and hosts can trigger it from the admin panel. Formed teams that no longer fit get a `rank_warning`; nothing is changed automatically.
- `app_settings.teams_frozen` (toggled by hosts) blocks every player-side team change: inviting, accepting, renaming, banners and disbanding (`require_unfrozen` in `handlers/team.rs`). It also freezes ranks: no daily, manual or on-demand refresh (`rank_refresh.rs`), and logging in keeps the stored rank. Cancelling or declining invites and all host actions still work.
- Only users with no role or just Streamer play (`Roles::can_play`); other staff are filtered out of the search and can't invite or accept. Inviting and accepting also need a linked Discord account.

### Matches, qualifiers and the bracket

- `matches` holds what every match has: `starts_at` (only qualifiers require it), one `referee_id`, staff-only `referee_notes` and `concluded_at`. Its osu! multiplayer rooms are in `match_rooms` (`mp_id` is the primary key, so a room belongs to one match; rendered as `osu.ppy.sh/community/matches/<id>`), oldest first by `added_at`. Usually there's one, but a room that breaks mid-match is replaced and the old one stays listed. Responses carry them as `rooms: [{ mp_id, url }]`, and the frontend shows them with `RoomLinks` (public) and `RoomsEditor` (`pages/admin/MatchControls.tsx`, for adding and removing). `kind` is a `match_kind` enum (`qualifier`, `bracket`); each kind adds its own tables. The shared running routes (referee, rooms, notes, conclude, reopen) are in `handlers/matches.rs` / `db/matches.rs`; conclude and reopen hand bracket matches to `handlers/bracket.rs`.
- Qualifiers are lobbies: hosts create them by time, and teams sign up through `qualifier_entries` (`team_id` is the primary key, so one lobby per team), at most `LOBBY_SIZE` (7) per lobby. Lobbies are numbered by start time at display, not stored.
- Either player can join, switch or leave until their current and target lobby start (`starts_at`) or are concluded. Signups lock the target lobby row so a lobby can't overfill. Hosts can move or remove any team at any time, still within the size limit.
- Running a match (`/api/matches/:id/*`): a referee takes a free match or gives up their own, which makes them its referee: the one Discord pings, asks to confirm a new time and lists on the match. Running it isn't limited to them: any referee (or host) can, so one can step in when the assigned one can't (`require_runs`, `canRun` on the referee page, the bracket panel and the lobby cards). A referee or a host adds or removes rooms (`POST /api/matches/:id/rooms`, `DELETE …/rooms/:mp_id`; removing one keeps its saved chat), writes notes and concludes it (which needs a room). After conclusion only notes stay editable for the referee; hosts can still change the rooms (a concluded match keeps at least one), reassign the referee and reopen it.
- `referee_notes` must never reach `/api/public/qualifiers`; it is only on the `StaffLobby` struct. The referee's Discord is public on purpose (players contact them there), as is every staff member's; players' Discord accounts are staff-only. The `teams_frozen` flag does not affect qualifier signups.
- Bracket matches (`handlers/bracket.rs`, `db/bracket.rs`): `bracket_matches` adds a side (`winners`/`losers`) and a stable number within it (shown as W1, L3; new matches get max+1), a position on the editor's board (`pos_x`, `pos_y` in 20px board units, so cards snap to a grid; unbounded, so either can be negative; every card is 12×5 units), two team slots, the score, a `streamer_id` and a `stage_id` (the stage, and so the map pool, it's played in; `ON DELETE SET NULL`, editable even once concluded). `bracket_links` says where a match's winner and loser go (target match + slot 1/2); the PK and `bracket_links_target_key` give each outcome one destination and each slot one source, and edits reject links that loop back.
- Concluding a bracket match needs both teams, a score with a winner and a room, and writes the winner and loser into their linked slots in one transaction. Reopening (host-only) takes them back out, unless a host has changed that slot since. Both refuse while a linked target is concluded. A concluded match's teams, links and score can't be edited until it's reopened.
- Forfeits: a referee or a host can conclude a bracket match by forfeit (`POST /api/bracket/:id/forfeit` with the slot that forfeited, from the referee page's "Hükmen bitir…" or "Hükmen…" in the bracket editor's panel) when a team doesn't show up or the match can't be finished. It needs both teams but no room or score; `bracket_matches.forfeit_slot` records the team that forfeited, the other one wins (`outcome` in `handlers/bracket.rs`, `winningSlot` in `lib/bracket.ts`), and the score shows as W / FF everywhere (`scoreHalves`, `messages::result_line` for Discord). Reopening clears it.
- Live scores: a match is live (`isLive` in `lib/bracket.ts`) once its time has come and it has a room, until it's concluded; its `team1_score`/`team2_score` are then the running score. The referee page saves it as it changes (below), the bracket views mark live matches with `components/LiveMark.tsx` (the glowing "Canlı" dot) and the fixture rows show the running score instead of "vs". Saving a score also queues a `SyncMatch`, and the Discord match card shows the running score ("Canlı skor") while the match has a room.
- Live updates (`handlers/live.rs`, `live/LiveContext.tsx`): every tab keeps one WebSocket to `GET /api/live` (anyone, Origin checked), mounted at the app root. The score route pushes `score` with the new figures after it commits; the other bracket and match changes (create, edit, delete, staff, rooms, conclude, reopen, forfeit, an accepted reschedule) push `bracket`, and pages reload the bracket (gathered over 250 ms, and again after a reconnect). The landing page, `/bracket`, the admin bracket (unless moves are still waiting to be saved) and team match histories listen through `useLiveBracket`. The referee page listens on its own (`useRefereeRoom.ts`): `score`, `match` and `referee` for its match and every `bracket` reload it, so every referee and host on a match sees the same; a reload the socket asked for never saves the score from that page (`remote`), since whoever made the change saved it and this page's chat may be behind. `lib/useLiveRefresh.ts` polls every 30 s only while the socket is down (the referee page polls itself then). When adding a bracket change, call `state.live.bracket_changed()` (or `score`) after the commit; a change to one match the bracket doesn't show (bans, picks, hand-awarded results, a lobby's teams) calls `state.live.match_changed(id)` instead, which only that match's public page and referee pages react to (`useLiveBracket` ignores it); a change only the referee page shows (its room options, "Sayma", the results source) calls `state.live.referee_changed(id)`, a `referee` event sent to staff only. A tab can also `watch` a match (`watch` in `LiveContext`, sent again when its rooms change, since the server looks them up then): it's then sent `chat`, every line the relay saves in that match's rooms (`RoomLog` in `handlers/irc.rs` pushes each saved row, filtered per tab by room). Watching also counts the tab among the match's spectators (only a match that has a room; nothing stored): every tab watching it hears `spectators`, the signed-in viewers by osu! name (each user once) and how many tabs nobody is signed in on (`guests`), whenever that changes; the public match page shows it in its header's live capsule, beside the page's one "Canlı" (`pages/match/MatchSpectators.tsx`: the count, and the names on a click).
- Referee-page presence: the referee page tells the socket which match it shows (`viewing`, referees and hosts only), and staff who can open the admin bracket hear each match's list of viewers (`presence`, and `presence_all` on connect), each user once. Nothing is stored; a closed tab or socket drops out, and the socket closes on `pagehide` so a page in the back/forward cache doesn't linger. The admin bracket shows it as an eye with the count on grid cards, list rows and the match panel (`components/bracket/RefereeWatchers.tsx`, names on hover, focus or tap), and the referee page lists everyone on it under its header.
- Hosts build the bracket; a referee (or a host) enters the score. Streamers take a free match or give up their own like referees do, but not a match their own team plays in; hosts can assign anyone holding Streamer. `/api/bracket` (with notes and player Discords) is for referees and hosts; the other staff (streamers can play) get the public data in the admin tab.
- Players reschedule their own bracket matches (`handlers/reschedule.rs`, `db/reschedule.rs`, shown by `components/MatchReschedules.tsx` on `/team`): `match_reschedules` holds times either team of a match has proposed (any number, up to `PROPOSAL_LIMIT` (10) per team per match, one row per time). Any player of the other team accepting one sets `matches.starts_at` and drops every proposal for the match, from both sides; either team can cancel or decline. Only for matches with both teams, until the match has a room or its current time has passed (`open`); the match row is locked for proposing and accepting. A host taking a team out of a match drops that team's proposals, and concluding drops the rest. `teams_frozen` doesn't affect it. An accepted move notifies the staff (below).
- Notifications (`handlers/notifications.rs`, `db/notifications.rs`, the bell in `components/NotificationBell.tsx`, shown in the top bar for every signed-in user) are one `notifications` row per recipient, about a match (`match_id`) or a team (`team_id`), with what happened copied in (times, ranks, team value) and the match's code and team names read when listed. When players move a match, its referee and streamer each get a `confirm_time` and every other host a `match_rescheduled`; a newer move deletes the unanswered `confirm_time`s of the older one. Confirming only records the answer. Declining takes them off the match (`referee_id` / `streamer_id` set to null) and sends `staff_declined` to everyone who could take the slot: the holders of Referee for a referee, the holders of Streamer who don't play in the match for a streamer (a host only if they hold that role). An answer needs the user to still hold that slot and the match to be unconcluded and still at that time (`actionable` in the list); it locks the match before the notification, like accepting a reschedule. The bell polls `/api/notifications/count` every minute and counts unread notifications plus unanswered actionable ones; opening the panel marks everything read. A host moving an unconcluded match to a future time in the bracket editor asks its referee and streamer the same way (`ask_confirm_time`, minus the host who moved it; `by_host` on the notification, and a `ConfirmTime` job for the Discord DMs), but tells no other hosts; other host edits notify no one.
- Players get two kinds, which link to `/team` (hosts' copies of the rank one to `/admin/teams`). `reschedule_proposed`: a proposal notifies both players of the other team, unless they still have an unread one for that match, so one notice covers every proposal made before it's read; the list shows how many of the opponent's proposals are still open (`pending_proposals`). `rank_over_limit`: whenever ranks are written (`rank_refresh::refresh`, which every refresh path goes through, and the osu! login upsert), `rank_refresh::notify_over_limit` checks the teams of the users whose rank changed and tells the players and the hosts when a team that was within the limit (or unranked) is now over it, naming the member whose value rose the most (`over_limit_cause`, unit-tested). A team that stays over isn't told again; one that drops back under and goes over again is. Losing a rank (`unranked`) doesn't notify.

### Public match page

- `/match/:matchId` (`pages/match/`) is the referee page's cockpit for everyone, live: the pool with the draft (`PoolView`), the room bar, the map clock (`MapClock`), the players in their slots with their mods and scores (`PlayersView`), the score sheet (`ScoreSheet`) and the room's chat (`MatchChat`), with the same phone tabs (`useCockpit`, `CockpitTabs`). Those pieces are exported from `pages/admin/referee/` and shared with the referee page, which fills in its controls (Discord pings, invite/move, ban/pick buttons, "Sayma", hand-awarded results, forfeits); the public page imports their CSS. It reads `GET /api/public/matches/:id` (`PublicMatch` in `handlers/referee.rs`: no referee notes, players without Discord, the pool only once its stage is published) and `GET /api/public/matches/:id/chat`, then follows the live socket (`useMatchPage.ts`): only while the match is live (a room, not concluded) does it `watch` the match and get `chat` lines as they come (and poll while the socket is down); a concluded match shows its saved chat. `score`, `match` and `bracket` reload the match either way, so a reopened match goes live again and an upcoming one starts streaming once its room is added. The room's state is read from the chat with the referee page's own helpers (`readLobby`, `currentPoolEntry`, `mapStartTime`, `rosterOf`); a bracket match's sheet and score are what its referee saved (`savedTally`), a lobby's maps come from the chat. Until it's concluded the public page heads each team in `PlayersView` with its banner (`banners`). Once a match is concluded the room's state is left out: the public page shows the teams as `TeamCard`s (the teams page's ruled cards, each ruled in its side's colour) and drops the map clock and the pool's "Odada" mark; the referee page's `PlayersView` (`finished`) lists them as a roster without slots, ready states, mods or who's in the room. "Sadeleştir" in the chat (on by default, in localStorage) hides `isRoomNoise` lines (`lib/bancho.ts`: BanchoBot's housekeeping, each player's "finished playing" and `!mp` commands; maps set, started, finished and rolls stay).
- Links to it (`components/MatchPageLink.tsx`, `matchPagePath`/`hasMatchPage`/`fixturePath` in `lib/bracket.ts`): every bracket match with both teams and every lobby. Fixture rows lead to it (a live one says "Canlı takip et"), and grid cards, calendar chips, list rows, the public bracket's selection bar, lobby cards, the team page's lobby and the admin match panel carry the link, frost while the match is live ("Canlı takip et"). On `/admin/*` the link renders nothing for those allowed Referee (referees and hosts), who open the referee page instead. Discord's match card and announcement have a "Maç sayfası" field, every match embed's title links to it (`messages::match_page_url`), and so do the "maç bitti" post and the results post.

### Referee page and Bancho IRC

- `/admin/referee/:matchId` runs a match (there's no list page: referees open it from a lobby on `/admin/qualifiers`, or from a bracket match on `/admin/bracket`, where every view has a `RefereeRoomLink` and so does the match panel): the teams with their Discords, the osu! room's slots, the Bancho chat and the map pool. `GET /api/matches/:id/room` (`handlers/referee.rs`, referees and hosts) returns all of it in one response: a lobby's teams in signup order, or a bracket match's two teams with `team1_id` blue and `team2_id` red (the room seats blue in slots 1-2 and red in 3-4; `SIDE_COLOR`/`SIDE_SLOTS` in `lib/bancho.ts` are the one place that says so, and every head-to-head on the site, Discord's 🔵/🔴 included, follows it), plus the stage's pool (a lobby uses the `is_qualifier` stage). Maps come from the `Public*` structs, so they carry no editor notes.
- Browsers can't speak IRC, so `GET /api/irc` (`handlers/irc.rs`, referees and hosts, Origin checked against `FRONTEND_URL`) is a WebSocket relay to `BANCHO_IRC_ADDR` (default `irc.ppy.sh:6667`). It logs in with the referee's own osu! IRC credentials, which stay in memory and are never stored or logged. It also answers PINGs, paces outgoing lines (at most 8 per 5 s, so Bancho doesn't mute the referee), and forwards PRIVMSGs plus our own JOIN/PART as JSON. Every line said in an `#mp_<id>` channel, including our own and BanchoBot's, is saved to `room_chat_messages` for moderation. Rows are keyed by `mp_id`, not by match, so the setup lines sent before the room is added to its match are kept too. Private messages aren't saved. Every referee in a channel sees the same lines, so only one relay connection saves each room (`ChatLoggers` in `AppState`: the first connection to see a line there; the next one takes over when it leaves). `GET /api/matches/:id/chat` (referee+) returns the saved log of each of a match's rooms. Bancho rejects a bad login by sending a MOTD and hanging up, so any close before `001` counts as a failed login. Each user has at most one Bancho connection (a session in `IrcUsers`, in `AppState`), shared by all of their tabs, so a referee running two matches side by side is still one account sending at one account's pace. A tab's first message is `login` (joins the session if there is one, whatever it typed, otherwise starts it) or `resume` (joins it, or gets `no_session`); a tab joining later gets `connected`, its joined channels and its private messages as a backlog, then every event. The session ends when its last tab closes or any tab sends `quit` ("Bağlantıyı kes"). All sessions come from the server's address, so after 3 failed logins a user waits 5 minutes before trying again (an attempt counts as failed until `001`, unless it never reached Bancho). The relay has no match logic; it only picks which tab runs each room's automation (below).
- Everything else happens in the frontend. `irc/IrcContext.tsx` holds the tab's socket and chat history; it's mounted in `AdminLayout`, so the connection survives switching pages. For referees it resumes the user's session on load and again when another tab of the browser comes online (a `BroadcastChannel`), so only the first tab asks for the password. Every tab shows the same private messages: the session keeps its last 500 in memory (never in the database) and sends them to a tab that joins as `past_message`s, numbered by `seq` so a tab rejoining the same session (`connected.session`) skips the ones it has. They get negative ids, like saved room lines, so they don't count as unread, and they don't reach `onMessage` listeners. Closing a DM tab closes it in every tab (`close`, answered with `conversation_closed`) and drops it from the session's history; closing a room tab only hides it in that tab. `lib/bancho.ts` folds BanchoBot's lines in the room channel into the room state (slots, teams, map, scores) and builds `!mp` commands. `pages/admin/referee/useRefereeRoom.ts` owns the page's data and command sequences. "Oda oluştur" sends `!mp make <ROOM_PREFIX>: (Team A) vs (Team B)`, waits for BanchoBot's "Created the tournament match" reply (one `!mp make` at a time across the browser's tabs, through a Web Lock, since every tab sees that reply), adds the room to the match, then sends `!mp set` (Team Vs for bracket matches, Head to Head for qualifiers; Score V2 by default; size = player count), `!mp lock`, an `!mp invite #<osu_id>` per player and `!mp settings`. In a bracket match the referee also marks bans and picks on the pool: `match_bans` and `match_picks` hold one row per pool map with the team that banned or picked it (one of the match's two), set and removed through `PUT`/`DELETE /api/bracket/:id/bans|picks/:map_id` by a referee or a host until it's concluded, and returned as `bans` and `picks` by the room endpoint. A map can't be both banned and picked (the inserts check). The pool panel (`pages/admin/referee/pool.ts` has the shared labels and team colours) shows ban buttons until there are `BAN_LIMIT` (2) bans, then pick buttons (none for TB); a pick also sets the map in the room. The page is a cockpit one screen tall under a one-line header: pool | match | chat, each scrolling on its own. On a phone (the page under 760px wide) it shows one of them at a time under a tab bar (Havuz / Maç / Sohbet) that sticks below the top bar (`--nav-height`, set by `NavBar`), each tab showing where its panel stands: the ban count or the next picker, the running score with the live dot while a map plays, and the chat's unread lines or the Bancho connection; the chat keeps lines unread while it's behind another tab (`visible` on `ChatPanel`). The pool column shows the bans and picks so far as team-coloured chips; the chat column starts with the Bancho login. The match column (`LobbyPanel.tsx`) reads top to bottom: the room bar (its links, options and "Odayı kapat" behind the settings button), the map clock, the players, the commands, then the score over the map results. It lists the match's players by team (`RoomPlayers.tsx`, blue beside red; the teams and the room's slots in one view), each pinned to their row in slot order (`RosterPlayer.home`: team 1's players take 1 and 2, team 2's 3 and 4, in the order the team lists them) whatever slot they're in, with the slot they're in as a chip in the colour of the team the room has them on, their ready state or score, the mods they picked under freemod (`RoomSlot.mods`, as acronyms, from the last `!mp settings`; "?" until read), their Discord and, while they're away, an invite button; anyone in the room who isn't in the match is listed after. A player out of their slot or colour gets a danger dot on their slot chip (where they belong is in its tooltip), and clicking any slot chip opens the slot picker: every slot with who holds it, the two colours and "Yerine gönder". Moves go through `moveCommands` in `lib/bancho.ts`: a slot another player holds is swapped (they wait in a free slot, the room growing by one when it's full and shrinking back after); given the match's slots (`matchSlots`), someone in them who isn't a match player is moved out past them instead and stays there. Each move ends with `!mp settings`, since Bancho barely answers `!mp team`. "Yerleri düzelt" places every player (`placeCommands`, each move counted in for the next). Only the match's players and holders of Host, Referee or Streamer (`useRoomStaff`/`staffRole` in `pages/admin/referee/roomStaff.ts`, from `GET /api/public/staff`) belong in the room. Everyone else in it is listed under the players (staff named by their role, with no button; anyone else with "Odadan at" and, for several, "Hepsini at", which send `!mp kick`), and the public page names the staff there too. Its commands sit under the players, above the map results. The results list each finished map of the pool (matched by beatmap id, and when the pool has that beatmap more than once, by the mods it was played with, then by the picks: `entryOf` in `pool.ts`; anything else, like a warmup, is left out and not counted) with its pool label, each player's score and mods (from the chat they're the room's plus the player's own from that `!mp settings`; osu!'s record has them per score, and a map counts as freemod there when a player had mods the room didn't), the winner in its team's colour and who picked it; "Sayma" leaves a pool map out of the score. The referee can also award a map (or a point without one) to a team by hand, with an optional note, for a map the room didn't settle: `match_manual_results`, added and removed through `POST /api/bracket/:id/results` and `DELETE …/results/:result_id` by a referee or a host until it's concluded, returned as `manual_results` by the room endpoint, counted with the room's results and listed in the Discord results post. The score (`tally` in `useRefereeRoom.ts`) is shown at the top of the match column's score sheet (`MatchHistory.tsx`) and saved through `PUT /api/bracket/:id/score` whenever it or the maps behind it change while the page is open (a map finishes, a result is awarded, a map is left out), so the site shows it live; not on the first reading after the page loads, so a score entered elsewhere isn't overwritten until the referee saves it by hand. The save carries the counted pool maps with each team's summed score (`maps`), which replace `match_map_results` and each player's score and mods on them, `match_map_scores` (returned as `map_results` with `players` by the room endpoint; a row's pool map goes null if the map is deleted, keeping its scores). Once a bracket match is concluded the page lists those saved results instead of reading the chat again; the Discord results post lists them. The finished maps are read from each room's chat, or, once the referee clicks "Maç linkinden eşitle" (for when the chat missed something), from osu!'s record of the rooms (`GET /api/matches/:id/osu-games`, referee+, `osu_api/matches.rs`; a room osu! has no record of falls back to its chat), which every referee page on the match then counts from (`match_room_settings.osu_synced_at`, set through `PUT /api/matches/:id/results-source`; each page reads osu!'s record itself, again when someone syncs anew and a few seconds after its chat sees a map finish) until "Sohbete dön". "Sayma" marks are keyed by source, room and the map's place in it, and saved in `match_ignored_maps` (`PUT /api/matches/:id/ignored-maps`). The commands also say whose pick is next (`nextPicker` in `pool.ts`: the roll's winner picks first and bans second, so the first pick goes to the team that didn't ban first, then picks alternate; the referee can override it until the next ban or pick: `match_room_settings.next_pick_team_id`, set through `PUT /api/matches/:id/next-pick` and cleared by marking or taking back a ban or pick; the public page shows it too, as `next_pick_team_id`) and "Skoru odaya yaz" sends the score and that line to the room (`AnnounceScore`, `scoreMessage`). The score sheet makes the two teams columns that run from the score down through every map, newest first: each map's totals sit in them with the winner's cell lit (an ignored map's stay unlit), and an opened map lists its players with each score in their team's column; the newest is open, the others open on click. While a map is played, the match column counts down its pool length (already mod-adjusted) from the latest room's last "The match has started!" line (`mapStartedAt`), so a reload keeps the clock; a map outside the pool counts up. Picking a pool map sends `!mp map` and `!mp mods` (NF added unless turned off; categories named FM/TB get Freemod). "Yeni oda aç" does the same to replace a broken room; the match's latest room is the one being played. The chat panel only shows the match's rooms and private messages: other matches' rooms stay hidden, even while the connection is still in them. Each room tab shows its saved log followed by the live lines that arrived after it was loaded (`pages/admin/referee/roomChat.ts`: saved lines get negative ids, and a live line that shows up just after loading and matches a recent saved one is skipped). So a reload, or a second referee, sees the whole chat. DM tabs can be closed (in every tab), and so can a room's tab once its channel is left (in that tab only). The page joins the latest room's channel once per connection, and never for a concluded match. The page is keyed by match. What it keeps besides bans, picks and results (the room options, "Sayma", the results source, the next-pick override) is saved per match (`match_room_settings`, `match_ignored_maps`; `handlers/referee.rs`, `db/referee.rs`), returned as `settings` and `ignored_maps` by the room endpoint, changed by a referee or a host until it's concluded (the controls are disabled for everyone else), applied on the page at once and saved in the background; so every referee and host on the match sees the same, and the saved score depends only on what the server has. What the page does in a room by itself keeps running for a match the referee has switched away from: moving bracket players to their slot and their team's colour as they join (the room option "Girenleri yerine ve takım rengine taşı"; the automation keeps its own copy of the room from BanchoBot's lines, refreshed by the page while it's open, so it knows who holds which slot), kicking whoever joins without belonging there ("Maç dışından girenleri at", on by default for every match, and only once the staff list has loaded; a join under a name no member has asks for `!mp settings` first and is settled by the osu! id it gives, so a player who renamed on osu! is placed rather than kicked), and sending `!mp settings` as each map starts so every player's mods are read. The page registers the room in `pages/admin/referee/roomAutomation.ts` (listened to by `<RoomAutomation />` in `AdminLayout`), and only one tab answers, in any browser: each tab asks the relay for the room (`automate` on its own socket, again after every reconnect) and `RoomRunners` in `handlers/irc.rs` picks one whose Bancho connection is in the room's channel, the match's own referee before everyone else (`pick_runner`, unit-tested); otherwise the runner keeps it until it leaves the channel or closes, and the next to ask takes over. Each tab hears `automation` (`running`, `waiting`, or `refused` once the match is concluded or gone). Changing the match's referee changes who comes first (`set_referee`), and concluding, forfeiting or deleting the match drops them all (`close`). The slots come from the latest room; the map results come from all of the match's rooms. Players address commands as `#<osu_id>`, and the slot parser accepts negative ids so the dev accounts work.

### Discord bot (`backend/src/discord`)

- Runs only when `DISCORD_BOT_TOKEN` and `DISCORD_GUILD_ID` are set (`DiscordBotConfig`, flattened into `Config`); `AppState.discord` is then `Some`. Everything it points at in the server (the Verified and Player roles, the team/match announcement, results, host, referee and streamer channels, and the open and archive categories for qualifier and bracket match channels) is picked by hosts on `/admin/discord` and stored in the single-row `discord_settings` (`db/discord.rs`); unset means the bot skips whatever needs it. It needs the privileged Server Members intent. Uses serenity (gateway + HTTP).
- Handlers never call Discord. They queue `discord::jobs::Job`s with `state.discord.enqueue(conn, &[...])` in the same transaction as the change (`discord_outbox`, woken by `pg_notify` on commit; nothing is queued while the bot is off), and one worker (`jobs.rs`) runs them in id order, retrying failures with backoff and dropping ones Discord refuses (4xx). The bot's HTTP client (`http_client` in `discord/mod.rs`) has connect/request timeouts, which serenity's lacks, and logs rate-limit waits of 2 s or more ("discord rate limit, waiting"). Serenity waits out rate limits by sleeping (a channel can be renamed twice per 10 minutes), so a job that runs over `JOB_TIMEOUT` (60 s; not `SyncAll`) is retried later instead of holding up the rest, and a channel rename is its own call waited on for at most `RENAME_WAIT` (5 s), recorded as not done when it times out so the next sync retries it. A message Discord refuses to delete is given up on with a warning, and a results post still on record is replaced, so a reopened match always gets its new post. Sync jobs reconcile Discord with the database: `SyncUser`/`SyncMember` (roles: Verified for a linked account, Player for a team member), `SyncMatch` (the match's channel), `SyncAll` (who's in the server, every member's roles, every match channel; queued on every gateway Ready, on saving settings and from the admin page; a member whose roles Discord refuses to change is logged and skipped, so one doesn't stop the rest). Event jobs (`TeamFormed`, `Rescheduled`, `Reminder`, …) are rendered by `messages.rs` (Turkish, like the site) into one `Post` job per destination, so a failed send retries alone. When adding a site action that Discord should know about, queue the job next to the website notification.
- Linking Discord (`handlers/auth.rs`) asks for `guilds.join` while the bot runs and adds the account to the server. `discord_accounts.in_guild` tracks membership (null until checked); the gateway's member add/remove events and `SyncAll` keep it current. A team member going from in to out gets a `discord_left` notification to their teammate and the hosts plus Discord messages; while out, they can't invite or accept (`require_in_server` in `handlers/team.rs`), and `/team` and `/admin/teams` show it.
- Match channels (`channels.rs`, `match_discord`): a bracket match gets one once it has both teams and a time, a qualifier lobby once a team signs up; an unconcluded match that loses a team again (reopening the match it came from takes it back out) has its channel deleted (`should_close`), and gets a new one once it has both again; visible to its players, referee and streamer (only accounts known to be in the server), hidden from everyone else (hosts are admins). An hour after a match is concluded (`ARCHIVE_AFTER_SECS` in `db/discord.rs`, so the players can still talk) it turns read-only and moves to the archive category: `MatchInfo.archived` is computed with the database's clock, and the scheduler queues the `SyncMatch` (`take_due_archives`, `match_discord.archived_for`); reopening moves it back; deleting the match archives it at once. The "concluded" and "reopened" posts in the channel replace each other (`Job::Post.status_of`, `match_discord.status_message_id`), so a reopened match doesn't keep its old result there. `match_discord.synced` records what was last applied, so an unchanged sync makes no API calls; syncs replace the channel's permission overwrites. The same sync keeps the channel's pinned card (`messages::match_card`: time, stage, teams, staff, rooms, result, and for a bracket match both teams' banners side by side; Discord shows the images of embeds sharing the main embed's url as one gallery, `OutMessage.gallery`, and banners are only linked when `FRONTEND_URL` is https, since Discord fetches them; the 15-minute announcement shows them too, and a banner change queues a `SyncMatch` for the team's open matches) in step: posted with the channel, pinging everyone in the match, then edited whenever it renders differently (`match_discord.card_message_id`/`card_synced`), so anything that changes what it shows has to queue a `SyncMatch`. Every change is also posted in the channel as plain text that pings the match's players, referee and streamer (`Pings::everyone`); only the card, the posts in the staff and host channels and the DMs are embeds, with anyone an embed should ping mentioned in its content (`OutMessage::embed`), since mentions inside an embed never ping. A full category (50) gets a sibling category created next to it (`discord_overflow_categories`).
- `scheduler.rs` (every 30 s): a reminder in the match channel an hour before a match, and the public announcement 15 minutes before a bracket match, pinging its `match_subscriptions` (spectators toggle them on `/bracket`). `match_discord.reminded_for`/`announced_for` hold the start time each was sent for, so a moved match gets them again. The public announcement is laid out like the match card (`messages::match_fields`, shared by both, naming people without pinging them) and kept up to date after it goes out (`discord/announcement.rs`, run by every `SyncMatch`; `match_discord.announce_message_id`/`announce_synced`, compared like the card): the live score while the match has a room, "ertelendi" with the new time once it's moved (the next announcement for the new time deletes the old message), and "iptal edildi" once it loses a team or is deleted. A score saved for a match that was never announced for its current time (it was already past when the scheduler could have) posts the announcement then (`claim_late_announcement`, claimed like the scheduler's, so the two can't both post it) (`Job::AnnouncementCancelled` carries what the message needs, since the match is gone). A concluded match, forfeits included, has its announcement deleted, since its result goes to the results channel. Concluding a bracket match posts its results in the results channel from the site's data only (the map results the referee page saved, with each player's mods on FM/TB maps, the hand-awarded ones, bans, picks, with the rooms linked but never read from osu!); reopening deletes the message.
- Referees and streamers get confirm-time requests as DMs with buttons that call `handlers::notifications::answer_as`; a declined slot is offered in the referee or streamer channel, pinging everyone its `staff_declined` notifications went to (`declined_recipients`). The referee page pings a player in the match channel when their Discord name is clicked (`POST /api/matches/:id/ping`, 30 s cooldown per player). Team announcements skip a team when both its players were announced in the last 7 days (`discord_announced_players`).
- Slash commands (`commands.rs`: `/rank`, `/maclar`, `/takim`, `/gecmis`, `/mac`) are registered to the guild on every Ready.

### Frontend (`frontend/src`)

- `api/client.ts` wraps `fetch` with `credentials: "include"` and throws the server's error text. `api/types.ts` mirrors the Rust response structs by hand, so update it whenever a serialized struct changes.
- `auth/AuthContext.tsx` loads `/api/me` on startup. `RequireAuth access=…` guards routes (a role, which hosts always pass, or `"staff"` for any role); `/admin/*` needs any staff role but Graphics Designer and Commentator, `/admin/bracket` the `"matches"` roles, `/admin/qualifiers` and `/admin/referee/:matchId` need referee, `/admin/mappool` needs `"pool"` (editing needs map_pooler) and `/admin/stages|users|teams|rules|discord` need host. Stages are created, renamed, reordered and deleted on `/admin/stages` (`pages/admin/StagesAdminPage.tsx`); the map pool editor only picks, publishes and fills them. Admin tabs are listed with who can open them in `pages/admin/tabs.ts`. On `/admin/*` the top bar (`components/NavBar.tsx`) swaps the public links for those tabs, turns a tinted colour (`--color-admin-*` in `tokens.css`) with a "Yönetim panelindesin" label in the middle, and its right-hand "Yönetim" button becomes "Siteye dön", which goes back to the last public page. Coming back, `/admin` (`AdminIndexRedirect`) reopens the last admin page the user was on, with its query and including a referee room, as long as their role still allows it (saved per user in localStorage).
- The map pool editor lives in `pages/admin/mappool/`. `useStageEditor.ts` owns all of its data and API calls, and the `.tsx` files only render. Structural changes go through `run()`, which shows a busy state and then reloads the stage. Small edits (notes, colours, ordering) update local state first and save in the background.
- The bracket views live in `components/bracket/`: `BracketGrid` (cards on a board with SVG lines for winner/loser links, shown in a fixed frame that pans and zooms with a CSS transform rather than scrolling: drag empty space to pan, wheel/pinch/buttons to zoom, recenter fits every match; when editable, pointer dragging snaps to board units, cards can't overlap, arrow keys nudge and double-click adds; the overlap rule lives only in the frontend, `overlapsAny` in `lib/bracket.ts`), `BracketList` and `BracketCalendar`, shared by the public `/bracket` page and `pages/admin/bracket/`. The search in the page header (`BracketSearch.tsx`) is shared by all three: the list and the calendar only show the matches it finds, the grid dims the rest so the board keeps its layout. There, `useBracketEditor.ts` owns the data and API calls (moves update locally and save after a short debounce) and `MatchPanel.tsx` edits the selected match. Its referee and streamer controls (`StaffControls.tsx`: a select for hosts, take/give up buttons for everyone else) are also in the list view's rows, so those can be changed without opening the panel.
- Every `TeamCard` (the teams pages and the `TeamPopover` used by the bracket and qualifier views) has a "Maçlar" button that blurs the card and lays the team's next bracket match and match history over it (`components/TeamMatches.tsx`, built from `/api/public/bracket`); `/team` turns it off and shows `TeamMatches` in its own section instead. Each match links to `bracketMatchPath` (`/bracket?match=<id>`, or `/admin/bracket` from an admin page), which both bracket pages read with `useLinkedMatch`: it switches to the grid, selects the match, centres on it (`BracketGrid`'s `centerOn`) and drops the parameter.
- `player/PlayerContext.tsx` and `components/MiniPlayer.tsx` provide an app-wide song preview player.

Frontend conventions (from `frontend/README.md`):
- Each component keeps its CSS next to it (`MapCard.tsx` + `MapCard.css`). Colours, spacing and font sizes come from the variables in `styles/tokens.css`.
- Icon-only buttons use `<IconButton label="…">`; new icons go in the `ICONS` map in `components/Icon.tsx`.
- Anything done by dragging also needs a button/select alternative (e.g. "Move to…" on map cards).
