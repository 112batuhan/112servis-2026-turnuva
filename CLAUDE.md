# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

An osu! tournament site: a Rust (axum + sqlx/Postgres) backend and a React + TypeScript (Vite) frontend. Users log in with osu! OAuth, can optionally link Discord, and map poolers build per-stage map pools that are published to a public page.

## Commands

A single `.env` at the repo root (copy from `.env.example`) feeds the backend (dotenvy searches parent dirs), the frontend (`envDir: ".."` in `frontend/vite.config.ts`, so only `VITE_*` vars reach it) and docker-compose.

```bash
# Backend (from backend/) — needs a reachable Postgres at DATABASE_URL
cargo run                 # serves on 127.0.0.1:8080, runs migrations on startup
cargo check / cargo clippy / cargo fmt

# Frontend (from frontend/)
npm install
npm run dev               # http://localhost:5173, calls the API at http://localhost:8080
npm run typecheck         # tsc only
npm run build             # tsc && vite build

# Everything in one container + Postgres
docker compose up --build # http://localhost:8080
```

There are no automated tests and no linter config for the frontend. `tsc` runs in strict mode with `noUnusedLocals`/`noUnusedParameters`, so unused code fails the typecheck.

For testing, set `DEV_LOGIN=true` in `.env`: the backend then mounts `/api/dev/*` (`handlers/dev.rs`) and the frontend bundles a floating account switcher (`components/DevSwitcher.tsx`, behind the build-time `__DEV_LOGIN__` constant from `vite.config.ts`) with buttons to reseed or clear dummy data. Dummy accounts have negative `osu_id`s (stages can't be marked that way, so the seed reuses stages by name and `clear.sql` only deletes seeded ones that have no categories); the seed lives in `backend/seed/` (it also gives W1 two rooms with saved chat, the first two upcoming matches some proposed times with the players' notices, Rank Uçtu a rank-limit notice, and every seeded stage the pool categories it's missing (by name), filled with real ranked maps added by DevPooler; `clear.sql` deletes the chat of the matches it removes and the categories holding only dummy-added maps) (also runnable with `psql "$DATABASE_URL" -f backend/seed/clear.sql -f backend/seed/seed.sql`, minus the team banners in `seed/banners/`, which `db/dev.rs` adds) and must be kept in step with schema changes. It defaults to off. It works over https too, so testers can use it on the live server while the site isn't public, but anyone who can reach the site can then sign in as any account (hosts included), so it must be turned off before launch.

The first host has to be set by hand in SQL: `UPDATE osu_users SET role = 'host' WHERE osu_id = <id>;`

## Architecture

### Backend (`backend/src`)

- `main.rs` builds `AppState` (oauth clients, `PgPool`, reqwest client, `Arc<Config>`, cached osu! app token) and mounts `/auth/*` (OAuth flows) and `/api/*` (JSON). If `STATIC_DIR/index.html` exists, it also serves the built frontend as a SPA fallback. This is how the Docker image serves both from one origin, with `VITE_API_URL` built empty.
- `config.rs`: clap `Config` from env vars, each also settable as a CLI flag. Whether cookies are `Secure` comes from the scheme of `FRONTEND_URL`.
- `handlers/<area>.rs` each expose `routes()`; `db/<area>.rs` hold the queries. Queries use runtime `sqlx::query_as::<_, T>(...)`, not the compile-time `query!` macros, so building needs no database.
- `error.rs`: handlers return `Result<_, AppError>`. Clients only get a generic message; 5xx causes go to the log. Add a new variant there instead of returning raw status codes.
- Migrations in `backend/migrations` are embedded with `sqlx::migrate!` and run on startup. Add a new numbered file and never edit an applied one.

### Auth and roles

- Server-side sessions (`auth.rs`, `db/session.rs`). The httpOnly `session` cookie holds a random 32-byte hex token, and the `sessions` table stores only its SHA-256, with a fixed 7-day expiry and no sliding renewal. The `AuthUser` extractor does one query per request that joins the session, `osu_users.role` and whether a Discord account is linked. Use `Option<AuthUser>` for routes that also work signed out.
- Create and end sessions only through `auth::start_session` / `auth::end_session`; they keep the cookie attributes and the stored hash consistent.
- `auth::spawn_session_cleanup` (started in `main.rs`) is a background tokio task that deletes expired sessions once at startup and then hourly.
- Roles form a ladder: `basic < streamer < referee < map_pooler < host` (`role.rs`, mirrored in `frontend/src/auth/roles.ts`), so map poolers can also referee and referees can also stream. Separately, `Role::can_play` (`canPlay` on the frontend) lets basic users and streamers be in teams; the rest of the staff can't. Gate handlers with `user.require_role(Role::X)?`. All `/api/stages|categories|slots|pool|maps` routes go through `guard()` in `handlers/mappool.rs` (MapPooler+), except that creating, renaming, reordering and deleting stages is Host-only; map poolers still publish stages and fill them. User admin is Host-only.
- Because the role is read on every request, role changes and logouts take effect immediately. No cookie needs re-issuing.

### Map pool domain (the core of the app)

The schema has changed a lot across migrations; the current model is:

- `stages` (ordered by `position`, with a `published` flag) → `stage_categories` (ordered, with a `color` `#rrggbb`) → `category_slots` (ordered, with `editor_notes`).
- At most one stage has `is_qualifier` (partial unique index `stages_qualifier_key`): the map pool the qualifier lobbies play. Hosts pick it on `/admin/stages` (`PUT /api/stages/qualifier`); bracket matches point at their stage with `bracket_matches.stage_id` instead.
- `pool_maps` holds each map **self-contained**: the beatmap metadata plus the mod-adjusted stats are copied in when the map is added, and there is no beatmap cache table. `slot_id IS NULL` means the map is in the global **generic pool** shared by all stages. Otherwise it fills exactly one slot (`UNIQUE(slot_id)`). Deleting a slot sends its map back to the generic pool. The same beatmap under different mods is a separate row.
- Mods are a concatenated 2-letter acronym string (`"HDDT"`) stored on the map. Stats are fixed when the map is added (`resolve_stats` in `handlers/mappool.rs`): SR/AR/OD come from the osu! difficulty-attributes API (skipped for nomod), and CS/BPM/length are computed in `mods.rs`. They are never recomputed later. HP is not stored.
- Public vs editor views: `editor_notes` (on slots and maps) must never reach the `/api/public/*` routes. These routes use separate `Public*` row structs and only return published stages. Keep that split when adding fields.
- osu! API calls (`osu_api/`) use an app token from the client-credentials flow, cached in memory in `AppState.osu_app_token`.

### Teams (2v2)

- `teams` / `team_members` (a player's `user_id` is the primary key, so one team per player) / `team_invites`. A team is created with both players when an invite is accepted, and doing so drops every other invite involving either of them.
- Eligibility is `team_rank.rs`: each rank maps to a value and the pair's sum must stay at or below `LIMIT`. It's checked when inviting and again when accepting (`handlers/team.rs`).
- The inviter names the team on the invite; the name moves to `teams.name` on accept and is unique case-insensitively (`teams_name_key`). Either player can rename or disband their team, and hosts can rename or disband any team.
- Banners live in `team_banners` as bytes (small app, no object storage). The type comes from the file's magic bytes, uploads are capped at 2 MB, and `Team.banner_url` carries the upload time as a version so the image can be cached forever.
- Ranks come from osu! through `rank_refresh.rs`, using the bulk `GET /users` endpoint (50 ids per call, osu!standard stats, no country rank). The player search, the team page, inviting and accepting refresh the users involved when their rank is over 10 minutes old (`osu_users.rank_updated_at`); failures fall back to the stored ranks. Every team member is refreshed daily (a background task checks hourly against `app_settings.ranks_updated_at`, so restarts don't skip or repeat it) and hosts can trigger it from the admin panel. Formed teams that no longer fit get a `rank_warning`; nothing is changed automatically.
- `app_settings.teams_frozen` (toggled by hosts) blocks every player-side team change: inviting, accepting, renaming, banners and disbanding (`require_unfrozen` in `handlers/team.rs`). It also freezes ranks: no daily, manual or on-demand refresh (`rank_refresh.rs`), and logging in keeps the stored rank. Cancelling or declining invites and all host actions still work.
- Only `basic` users and streamers play (`Role::can_play`); other staff are filtered out of the search and can't invite or accept. Inviting and accepting also need a linked Discord account.

### Matches, qualifiers and the bracket

- `matches` holds what every match has: `starts_at` (only qualifiers require it), one `referee_id`, staff-only `referee_notes` and `concluded_at`. Its osu! multiplayer rooms are in `match_rooms` (`mp_id` is the primary key, so a room belongs to one match; rendered as `osu.ppy.sh/community/matches/<id>`), oldest first by `added_at`. Usually there's one, but a room that breaks mid-match is replaced and the old one stays listed. Responses carry them as `rooms: [{ mp_id, url }]`, and the frontend shows them with `RoomLinks` (public) and `RoomsEditor` (`pages/admin/MatchControls.tsx`, for adding and removing). `kind` is a `match_kind` enum (`qualifier`, `bracket`); each kind adds its own tables. The shared running routes (referee, rooms, notes, conclude, reopen) are in `handlers/matches.rs` / `db/matches.rs`; conclude and reopen hand bracket matches to `handlers/bracket.rs`.
- Qualifiers are lobbies: hosts create them by time, and teams sign up through `qualifier_entries` (`team_id` is the primary key, so one lobby per team), at most `LOBBY_SIZE` (7) per lobby. Lobbies are numbered by start time at display, not stored.
- Either player can join, switch or leave until their current and target lobby start (`starts_at`) or are concluded. Signups lock the target lobby row so a lobby can't overfill. Hosts can move or remove any team at any time, still within the size limit.
- Running a match (`/api/matches/:id/*`): a referee takes a free match or gives up their own; the match's referee or a host adds or removes rooms (`POST /api/matches/:id/rooms`, `DELETE …/rooms/:mp_id`; removing one keeps its saved chat), writes notes and concludes it (which needs a room). After conclusion only notes stay editable for the referee; hosts can still change the rooms (a concluded match keeps at least one), reassign the referee and reopen it. Other referees can see every match but not change it.
- `referee_notes` must never reach `/api/public/qualifiers`; it is only on the `StaffLobby` struct. The referee's Discord is public on purpose (players contact them there); players' Discord accounts are staff-only. The `teams_frozen` flag does not affect qualifier signups.
- Bracket matches (`handlers/bracket.rs`, `db/bracket.rs`): `bracket_matches` adds a side (`winners`/`losers`) and a stable number within it (shown as W1, L3; new matches get max+1), a position on the editor's board (`pos_x`, `pos_y` in 20px board units, so cards snap to a grid; unbounded, so either can be negative; every card is 12×5 units), two team slots, the score, a `streamer_id` and a `stage_id` (the stage, and so the map pool, it's played in; `ON DELETE SET NULL`, editable even once concluded). `bracket_links` says where a match's winner and loser go (target match + slot 1/2); the PK and `bracket_links_target_key` give each outcome one destination and each slot one source, and edits reject links that loop back.
- Concluding a bracket match needs both teams, a score with a winner and a room, and writes the winner and loser into their linked slots in one transaction. Reopening (host-only) takes them back out, unless a host has changed that slot since. Both refuse while a linked target is concluded. A concluded match's teams, links and score can't be edited until it's reopened.
- Hosts build the bracket; a match's referee (or a host) enters the score. Streamers take a free match or give up their own like referees do, but not a match their own team plays in; hosts can assign anyone streamer and up. `/api/bracket` (with notes and player Discords) is referee+; streamers can play, so the admin tab gives them the public data.
- Players reschedule their own bracket matches (`handlers/reschedule.rs`, `db/reschedule.rs`, shown by `components/MatchReschedules.tsx` on `/team`): `match_reschedules` holds times either team of a match has proposed (any number, up to `PROPOSAL_LIMIT` (10) per team per match, one row per time). Any player of the other team accepting one sets `matches.starts_at` and drops every proposal for the match, from both sides; either team can cancel or decline. Only for matches with both teams, until the match has a room or its current time has passed (`open`); the match row is locked for proposing and accepting. A host taking a team out of a match drops that team's proposals, and concluding drops the rest. `teams_frozen` doesn't affect it. An accepted move notifies the staff (below).
- Notifications (`handlers/notifications.rs`, `db/notifications.rs`, the bell in `components/NotificationBell.tsx`, shown in the top bar for every signed-in user) are one `notifications` row per recipient, about a match (`match_id`) or a team (`team_id`), with what happened copied in (times, ranks, team value) and the match's code and team names read when listed. When players move a match, its referee and streamer each get a `confirm_time` and every other host a `match_rescheduled`; a newer move deletes the unanswered `confirm_time`s of the older one. Confirming only records the answer. Declining takes them off the match (`referee_id` / `streamer_id` set to null) and sends `staff_declined` to everyone who could take the slot: referees and up for a referee, streamers and up who don't play in the match for a streamer (hosts are in both). An answer needs the user to still hold that slot and the match to be unconcluded and still at that time (`actionable` in the list); it locks the match before the notification, like accepting a reschedule. The bell polls `/api/notifications/count` every minute and counts unread notifications plus unanswered actionable ones; opening the panel marks everything read. Host edits in the bracket editor don't notify anyone.
- Players get two kinds, which link to `/team` (hosts' copies of the rank one to `/admin/teams`). `reschedule_proposed`: a proposal notifies both players of the other team, unless they still have an unread one for that match, so one notice covers every proposal made before it's read; the list shows how many of the opponent's proposals are still open (`pending_proposals`). `rank_over_limit`: whenever ranks are written (`rank_refresh::refresh`, which every refresh path goes through, and the osu! login upsert), `rank_refresh::notify_over_limit` checks the teams of the users whose rank changed and tells the players and the hosts when a team that was within the limit (or unranked) is now over it, naming the member whose value rose the most (`over_limit_cause`, unit-tested). A team that stays over isn't told again; one that drops back under and goes over again is. Losing a rank (`unranked`) doesn't notify.

### Referee page and Bancho IRC

- `/admin/referee/:matchId` runs a match (there's no list page: referees open it from a lobby on `/admin/qualifiers`, or from a bracket match on `/admin/bracket`, where every view has a `RefereeRoomLink` and so does the match panel): the teams with their Discords, the osu! room's slots, the Bancho chat and the map pool. `GET /api/matches/:id/room` (`handlers/referee.rs`, referee+) returns all of it in one response: a lobby's teams in signup order, or a bracket match's two teams with `team1_id` red and `team2_id` blue, plus the stage's pool (a lobby uses the `is_qualifier` stage). Maps come from the `Public*` structs, so they carry no editor notes.
- Browsers can't speak IRC, so `GET /api/irc` (`handlers/irc.rs`, referee+, Origin checked against `FRONTEND_URL`) is a WebSocket relay to `BANCHO_IRC_ADDR` (default `irc.ppy.sh:6667`). It logs in with the referee's own osu! IRC credentials, which stay in memory and are never stored or logged. It also answers PINGs, paces outgoing lines (at most 8 per 5 s, so Bancho doesn't mute the referee), and forwards PRIVMSGs plus our own JOIN/PART as JSON. Every line said in an `#mp_<id>` channel, including our own and BanchoBot's, is saved to `room_chat_messages` for moderation. Rows are keyed by `mp_id`, not by match, so the setup lines sent before the room is added to its match are kept too. Private messages aren't saved. Every referee in a channel sees the same lines, so only one relay connection saves each room (`ChatLoggers` in `AppState`: the first connection to see a line there; the next one takes over when it leaves). `GET /api/matches/:id/chat` (referee+) returns the saved log of each of a match's rooms. Bancho rejects a bad login by sending a MOTD and hanging up, so any close before `001` counts as a failed login. Each user has at most one Bancho connection (a session in `IrcUsers`, in `AppState`), shared by all of their tabs, so a referee running two matches side by side is still one account sending at one account's pace. A tab's first message is `login` (joins the session if there is one, whatever it typed, otherwise starts it) or `resume` (joins it, or gets `no_session`); a tab joining later gets `connected`, its joined channels and its private messages as a backlog, then every event. The session ends when its last tab closes or any tab sends `quit` ("Bağlantıyı kes"). All sessions come from the server's address, so after 3 failed logins a user waits 5 minutes before trying again (an attempt counts as failed until `001`, unless it never reached Bancho). The relay has no match logic.
- Everything else happens in the frontend. `irc/IrcContext.tsx` holds the tab's socket and chat history; it's mounted in `AdminLayout`, so the connection survives switching pages. For referees it resumes the user's session on load and again when another tab of the browser comes online (a `BroadcastChannel`), so only the first tab asks for the password. Every tab shows the same private messages: the session keeps its last 500 in memory (never in the database) and sends them to a tab that joins as `past_message`s, numbered by `seq` so a tab rejoining the same session (`connected.session`) skips the ones it has. They get negative ids, like saved room lines, so they don't count as unread, and they don't reach `onMessage` listeners. Closing a DM tab closes it in every tab (`close`, answered with `conversation_closed`) and drops it from the session's history; closing a room tab only hides it in that tab. `lib/bancho.ts` folds BanchoBot's lines in the room channel into the room state (slots, teams, map, scores) and builds `!mp` commands. `pages/admin/referee/useRefereeRoom.ts` owns the page's data and command sequences. "Oda oluştur" sends `!mp make <ROOM_PREFIX>: (Team A) vs (Team B)`, waits for BanchoBot's "Created the tournament match" reply (one `!mp make` at a time across the browser's tabs, through a Web Lock, since every tab sees that reply), adds the room to the match, then sends `!mp set` (Team Vs for bracket matches, Head to Head for qualifiers; Score V2 by default; size = player count), `!mp lock`, an `!mp invite #<osu_id>` per player and `!mp settings`. In a bracket match the referee also marks bans and picks on the pool: `match_bans` and `match_picks` hold one row per pool map with the team that banned or picked it (one of the match's two), set and removed through `PUT`/`DELETE /api/bracket/:id/bans|picks/:map_id` by the match's referee or a host until it's concluded, and returned as `bans` and `picks` by the room endpoint. A map can't be both banned and picked (the inserts check). The pool panel (`pages/admin/referee/pool.ts` has the shared labels and team colours) shows ban buttons until there are `BAN_LIMIT` (2) bans, then pick buttons (none for TB); a pick also sets the map in the room. The results list each finished map of the pool (matched by beatmap id; anything else, like a warmup, is left out and not counted) with its pool label, the winner in its team's colour and who picked it; "Sayma" leaves a pool map out of the score. Picking a pool map sends `!mp map` and `!mp mods` (NF added unless turned off; categories named FM/TB get Freemod). "Yeni oda aç" does the same to replace a broken room; the match's latest room is the one being played. The chat panel only shows the match's rooms and private messages: other matches' rooms stay hidden, even while the connection is still in them. Each room tab shows its saved log followed by the live lines that arrived after it was loaded (`pages/admin/referee/roomChat.ts`: saved lines get negative ids, and a live line that shows up just after loading and matches a recent saved one is skipped). So a reload, or a second referee, sees the whole chat. DM tabs can be closed (in every tab), and so can a room's tab once its channel is left (in that tab only). The page joins the latest room's channel once per connection, and never for a concluded match. The page is keyed by match, and each match's room options and "Sayma" marks are kept for the tab (`matchSettings` in `useRefereeRoom.ts`), so a referee can switch between two matches. Moving bracket players to their team's colour as they join keeps running for a match the referee has switched away from: the page registers the room in `pages/admin/referee/autoTeams.ts` (listened to by `<AutoTeams />` in `AdminLayout`), and a Web Lock per room picks the one tab that sends the `!mp team`. The slots come from the latest room; the map results come from all of the match's rooms. Players address commands as `#<osu_id>`, and the slot parser accepts negative ids so the dev accounts work.

### Frontend (`frontend/src`)

- `api/client.ts` wraps `fetch` with `credentials: "include"` and throws the server's error text. `api/types.ts` mirrors the Rust response structs by hand, so update it whenever a serialized struct changes.
- `auth/AuthContext.tsx` loads `/api/me` on startup. `RequireAuth minRole=…` guards routes; `/admin/*` (and `/admin/bracket`) needs streamer, `/admin/qualifiers` and `/admin/referee/:matchId` need referee, `/admin/mappool` needs map_pooler and `/admin/stages|users|teams` need host. Stages are created, renamed, reordered and deleted on `/admin/stages` (`pages/admin/StagesAdminPage.tsx`); the map pool editor only picks, publishes and fills them. Admin tabs are listed with their minimum role in `pages/admin/tabs.ts`. On `/admin/*` the top bar (`components/NavBar.tsx`) swaps the public links for those tabs, turns a tinted colour (`--color-admin-*` in `tokens.css`) with a "Yönetim panelindesin" label in the middle, and its right-hand "Yönetim" button becomes "Siteye dön", which goes back to the last public page. Coming back, `/admin` (`AdminIndexRedirect`) reopens the last admin page the user was on, with its query and including a referee room, as long as their role still allows it (saved per user in localStorage).
- The map pool editor lives in `pages/admin/mappool/`. `useStageEditor.ts` owns all of its data and API calls, and the `.tsx` files only render. Structural changes go through `run()`, which shows a busy state and then reloads the stage. Small edits (notes, colours, ordering) update local state first and save in the background.
- The bracket views live in `components/bracket/`: `BracketGrid` (cards on a board with SVG lines for winner/loser links, shown in a fixed frame that pans and zooms with a CSS transform rather than scrolling: drag empty space to pan, wheel/pinch/buttons to zoom, recenter fits every match; when editable, pointer dragging snaps to board units, cards can't overlap, arrow keys nudge and double-click adds; the overlap rule lives only in the frontend, `overlapsAny` in `lib/bracket.ts`), `BracketList` and `BracketCalendar`, shared by the public `/bracket` page and `pages/admin/bracket/`. The search in the page header (`BracketSearch.tsx`) is shared by all three: the list and the calendar only show the matches it finds, the grid dims the rest so the board keeps its layout. There, `useBracketEditor.ts` owns the data and API calls (moves update locally and save after a short debounce) and `MatchPanel.tsx` edits the selected match. Its referee and streamer controls (`StaffControls.tsx`: a select for hosts, take/give up buttons for everyone else) are also in the list view's rows, so those can be changed without opening the panel.
- Every `TeamCard` (the teams pages and the `TeamPopover` used by the bracket and qualifier views) has a "Maçlar" button that blurs the card and lays the team's next bracket match and match history over it (`components/TeamMatches.tsx`, built from `/api/public/bracket`); `/team` turns it off and shows `TeamMatches` in its own section instead. Each match links to `bracketMatchPath` (`/bracket?match=<id>`, or `/admin/bracket` from an admin page), which both bracket pages read with `useLinkedMatch`: it switches to the grid, selects the match, centres on it (`BracketGrid`'s `centerOn`) and drops the parameter.
- `player/PlayerContext.tsx` and `components/MiniPlayer.tsx` provide an app-wide song preview player.

Frontend conventions (from `frontend/README.md`):
- Each component keeps its CSS next to it (`MapCard.tsx` + `MapCard.css`). Colours, spacing and font sizes come from the variables in `styles/tokens.css`.
- Icon-only buttons use `<IconButton label="…">`; new icons go in the `ICONS` map in `components/Icon.tsx`.
- Anything done by dragging also needs a button/select alternative (e.g. "Move to…" on map cards).
