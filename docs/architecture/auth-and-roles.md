# Auth and roles

- Server-side sessions (`auth.rs`, `db/session.rs`). The httpOnly `session` cookie holds a random 32-byte hex token, and the `sessions` table stores only its SHA-256, with a fixed 7-day expiry and no sliding renewal. The `AuthUser` extractor does one query per request that joins the session, `osu_users.role` and whether a Discord account is linked. Use `Option<AuthUser>` for routes that also work signed out.
- OAuth (`handlers/auth.rs`): starting a flow puts its `state` in the server's `OAuthStates` (`auth.rs`, with the flow and, for the Discord link, the user who started it; 10 minutes) and in the httpOnly `oauth_state` cookie (`Path=/auth`). A callback only goes through with the same state in its query and the cookie, for the same flow, and a Discord link only for the user who started it, so a callback URL can't be handed to someone else. A callback that doesn't sign in or link redirects to `/?login_error=<code>` or `/discord?error=<code>` (`CallbackError`, snake_case; the pages show them in Turkish, `LOGIN_ERROR_TEXT`/`DISCORD_LINK_ERROR_TEXT` in `api/errors.ts`), never to an error page; a Discord account already linked to another osu! account is `taken`. Token exchanges use `AppState.oauth_http` (no redirects, timeouts).
- Create and end sessions only through `auth::start_session` / `auth::end_session`; they keep the cookie attributes and the stored hash consistent.
- `auth::spawn_session_cleanup` (started in `main.rs`) is a background tokio task that deletes expired sessions once at startup and then hourly.
- Roles are a set, not a ladder: a user holds any of `host`, `map_pooler`, `referee`, `streamer`, `graphics_designer`, `pool_tester`, `custom_mapper` and `commentator` (`osu_users.roles`, a `staff_role[]`; none means a regular player), ticked per user on `/admin/users` (`PUT /api/users/:id/roles`; a host can't drop their own Host). `role.rs` (`Roles`, a bitset on `AuthUser`) is mirrored in `frontend/src/auth/roles.ts`. Roles don't imply each other except that Host is allowed everything: `Roles::allows` (`hasRole`) is holding the role or being a host, and gates pages and actions (`user.require_role(Role::X)?`). Acting in a role needs the role itself, `Roles::has` (`holdsRole`): only holders of Referee/Streamer are offered for, can take and are pinged about those slots (`list_referees`/`list_streamers`, `staff_declined`), so a host who referees ticks Referee too. `Roles::can_play` (`canPlay`) lets users with no role or only Streamer, Graphics Designer and/or Commentator be in teams; the rest of the staff can't. Graphics Designer and Commentator carry no authority at all: they only list the user on `/staff`, and `isStaff` (which opens `/admin`) ignores them. All `/api/mappool/*` routes go through `guard()` in `handlers/mappool.rs` (MapPooler or host); creating, renaming, reordering and deleting stages is Host-only (map poolers still publish stages and fill them; the stages' own routes are `/api/stages` in `handlers/stages.rs` and their queries `db/stages.rs`). Listing stages and reading a stage's pool (`GET /api/stages`, `GET /api/mappool/stages/:id`) go through `view_guard()`, `Roles::can_view_pool` (`canViewPool`), which also lets in Pool Tester and Custom Mapper. Those two only get the Mappool tab (access `"pool"`), which the editor shows read-only to anyone not allowed MapPooler (no adding, moving, dropping, settings; notes shown but not editable, `readOnly` on `EditableNote`, `viewOnly` on `MapCard`); the Maçlar tab is access `"matches"` (holders of Host, MapPooler, Referee or Streamer). User admin is Host-only.
- Rules (`handlers/rules.rs`, `db/rules.rs`): the single-row `rules` table holds osu! BBCode (seeded by migration 0035 from the previous tournament's forum post). `GET /api/public/rules` serves it to `/rules` (`pages/RulesPage.tsx`, with a contents list built from its `[heading]`s); hosts edit it on `/admin/rules` (`pages/admin/RulesAdminPage.tsx`: source, toolbar and live preview) through `PUT /api/rules`, which sends the `updated_at` it loaded and gets a 409 if another host saved since. `lib/bbcode.ts` parses the forum's tags into a tree and `components/BBCode.tsx` renders it as React elements (never as HTML), letting links through only for http(s)/mailto and images only for http(s).
- The public `/staff` page (`pages/StaffPage.tsx`, "Ekip" in the nav) lists everyone holding a role, grouped by role (someone with two roles shows in both), from `GET /api/public/staff` (`db::user::list_staff`), which carries each one's linked Discord: staff Discord accounts are public on purpose.
- Because the roles are read on every request, role changes and logouts take effect immediately. No cookie needs re-issuing. Sockets outlive their request, so they keep the session (`auth::SessionKey`) and check it again when `Live::user_changed` says the user's roles changed or they logged out (`PUT /api/users/:id/roles`, `POST /auth/logout`), and every 5 minutes: a live socket whose staff or referee access changed is closed (the page reconnects with what they hold now), and the IRC relay closes once they no longer hold Referee.
